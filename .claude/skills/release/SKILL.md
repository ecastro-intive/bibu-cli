# release

Releases are built by GitHub Actions (`.github/workflows/release.yml`, generated by cargo-dist from
`dist-workspace.toml`) when a `v*` tag is pushed. `CONTRIBUTING.md` ("Releasing") is the reference;
this skill is the order of work and the gates. Pushing a tag **publishes** to users and cannot be
cleanly undone, so never run steps 5 and 6 without the user's explicit go-ahead in this session.

Run every git step with the `commit-message` skill's rules (branch, commit and PR title formats,
no footer). Push with `git -c credential.helper='!gh auth git-credential' push`.

## 1. Pre-flight

- On `main`, up to date: `git switch main && git pull --ff-only`. The working tree is clean.
- Everything meant for the release is merged. List what ships: `git log --oneline v<last>..HEAD`
  (`git describe --tags --abbrev=0` gives the last tag).
- `gh run list --branch main --limit 3` shows CI green on the latest `main` commit.
- `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` pass, and
  `UPDATE_DOCS=1 cargo test --test docs` leaves `git status` clean.

## 2. Pick the version

Semver. While the major version is 0: a new user-visible capability or output change is a minor bump
(`0.1.0` -> `0.2.0`), a fix only is a patch (`0.1.0` -> `0.1.1`). Say which you recommend and why,
and let the user choose. A breaking change to JSON output or exit codes is called out explicitly.

## 3. Smoke test (recommended)

`./scripts/smoke-release.sh` (macOS / Linux, needs `dist`; it takes a few minutes). It builds the
committed `HEAD` and a patched copy, installs the older with the real installer against a fake
GitHub, and checks `bibu upgrade` installs the newer. It only uses a temporary worktree and a
throwaway `HOME`. Expect the last line `==> OK: installed ..., upgraded to ..., and the second
upgrade was a no-op`. It covers the host platform only; Windows is covered by the real CI build.

## 4. Version bump PR

1. Branch `chore/release-<version>` from `main`.
2. Set `version = "<version>"` in `Cargo.toml` (the package, not a dependency), then refresh the
   lockfile: `cargo update -p bibu --offline` or simply `cargo build`. Only `Cargo.toml` and
   `Cargo.lock` should change.
3. Re-run the checks from step 1, then commit `chore: release <version>`.
4. Push and open the PR with `gh pr create`, same title. The PR run only does `dist plan`; it
   must be green. Ask the user to review and merge it (do not merge it yourself unless asked).

## 5. Tag (needs the user's explicit go-ahead)

After the bump PR is merged:

```sh
git switch main && git pull --ff-only
grep -m1 '^version' Cargo.toml        # must show the new version
git tag v<version>
git push origin v<version>            # this starts the release
```

Never move or delete a tag that was already pushed without the user asking. Never push to `main`
or force-push.

## 6. Watch and verify

- `gh run list --workflow release.yml --limit 1`, then `gh run watch <id>` until it finishes.
- `gh release view v<version>` lists the macOS and Windows archives, `bibu-installer.sh`,
  `bibu-installer.ps1` and checksums.
- Install with the published installer in a throwaway `HOME` and check the version:

  ```sh
  H=$(mktemp -d) && HOME=$H BIBU_NO_MODIFY_PATH=1 sh -c 'curl --proto "=https" --tlsv1.2 -LsSf \
    https://github.com/ecastro-intive/bibu-cli/releases/latest/download/bibu-installer.sh | sh' \
    && "$H/.local/bin/bibu" --version        # expect: bibu <version>
  ```
- If an older bibu is installed somewhere, `bibu upgrade --check` should now report an update.

## If the release workflow fails

Do not re-tag over it. Read `gh run view <id> --log-failed`, fix on a branch through a normal PR,
and ask the user how to proceed (usually a new patch version). Delete a bad tag or release only if
the user asks.

## Changing targets or installers

Edit `dist-workspace.toml`, run `dist generate` (`cargo install cargo-dist --locked --version
0.32.0`), and commit the regenerated workflow. This is a separate PR from a release.
